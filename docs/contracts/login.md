# Contract: login and account linking for the Studio client

Owner: studio-auth. Consumers: Studio client (`studio/src/auth`), server rooms (`server/rooms`). Server: web API (`web/server/auth/`).

Decided with the user on 2026-10-22: **four ways in, one PlayFab account per player, all in v1.** Progress is the PlayFab account; every method is only a way to open it, and a player can add the other methods later to the same account. PlayFab cannot merge two accounts, so the rules below always move an identity, never progress.

The Decentraland scene resolves its account with `POST /api/get-login-id`, which needs the explorer's signed auth chain (`chain-playfab/security/securityChecks.ts`). A browser game cannot produce that, hence this contract. The Sandbox account is NOT a method: the Studio hands the game no verifiable identity (checked 2026-10-22 against `@gnsx/genesys.js` 18 and the `studio.sandbox.game/play` bundles). When it does, it joins this list as one more method.

## Methods

| Method | PlayFab calls (Client REST, as `scene/src/meta/playfab-rest.ts`) | How the account is found | Needs |
|---|---|---|---|
| Wallet | `LoginWithCustomID` with the CustomId returned by `POST /api/login-wallet` | generic ID `address` (lowercase wallet), like the scene | MetaMask or any injected provider on desktop; WalletConnect v2 on phones and Telegram |
| Guest | `LoginWithCustomID {CustomId, CreateAccount: true}`; `CustomId` = 32 random hex generated by the client and kept in `localStorage` | that CustomId | nothing |
| Email | `RegisterPlayFabUser {Email, Password, RequireBothUsernameAndEmail: false}` to create, `LoginWithEmailAddress {Email, Password}` to log in, `SendAccountRecoveryEmail {Email}` for the forgotten-password link (PlayFab's default mail) | the email | nothing on our side |
| Google | `LoginWithOpenIdConnect {ConnectionId: "google", IdToken, CreateAccount: true}` with the ID token from the Sign in with Google button (Google Identity Services) | the Google account | a Google Cloud OAuth web client and the OpenID Connect connection `google` in PlayFab Game Manager (add-ons; issuer `https://accounts.google.com`, the web client id, nonce check off because GIS tokens carry none). The user sets both up. |

Every new account (guest, email, Google, or a wallet unknown to the title) runs the `initializePlayer` cloudscript exactly as `scene/src/meta/bootstrap.ts:initializePlayerAccount` does, then `UpdateUserTitleDisplayName`. The cloudscript links `user.publicKey` as the `address` generic ID: pass the wallet for wallet logins and **nothing identity-like for the others** (use the PlayFabId returned by the login), so only wallets ever live under `ServiceName: "address"`. `UserData.address` is written only for wallets (by the wallet login and by `link-wallet`), so the client reads "this account has a wallet" from it; email and Google come from `AccountInfo` (`PrivateInfo.Email`, `OpenIdInfo`).

Display names: wallet → the Decentraland profile name from the catalyst (`POST https://peer.decentraland.org/lambdas/profiles {"ids":[address]}`, as `web/lib/avatars.ts:fetchAvatars`), fallback `0x1234…abcd`; guest → `Golfer-<4 hex>`; email → a name typed at sign-up; Google → the Google name. 3 to 25 characters.

## Wallet endpoints (unchanged from the first version of this contract)

### `GET /api/login-wallet/nonce?address=0x…`

Response `200`: `{ "message": string, "expiresAt": number }`

- `message` is the exact text the wallet must sign (EIP-191 `personal_sign`), human readable, containing: product name, the lowercase address, a random nonce, `issuedAt` and `expiresAt` (5 minutes).
- The nonce is stateless: `HMAC-SHA256(secret, address + issuedAt)` so several web instances validate it; the secret is a new env var `LOGIN_WALLET_SECRET` (CapRover app `golfcraft-web`, local `web/.env`). Replay inside the window is prevented with an in-memory set of used nonces.
- `400` on a malformed address.

### `POST /api/login-wallet`

Body: `{ "address": "0x…", "message": string, "signature": "0x…" }`

Checks, in order: message parses and its address equals `address` (lowercased); `expiresAt` not passed; nonce HMAC valid and unused; `ethers.verifyMessage(message, signature)` equals the address. Any failure → `401 { "error": "…" }` without details that help an attacker.

Success `200`: `{ "CustomId": string }`, computed exactly like `/api/get-login-id`: `GetPlayFabIDsFromGenericIDs({ServiceName:"address", UserId: address})` → `GetUserAccountInfo` → `CustomIdInfo.CustomId`; unknown wallet → random 100-char CustomId (the client's `initializePlayer` then links the wallet, see `.claude/CLAUDE.md` §6 #24). Also calls `recordVisit(prisma, address)` for `/stats`.

Rate limit: 20 requests per minute per IP on both routes (express-rate-limit or a small in-memory counter).

### Visitors for `/stats`

`login-wallet` records the wallet in `daily_visit` (like `get-login-id`). Guest, email and Google logins must count too: `POST /api/record-visit` (`web/server/stats/index.ts`) only accepts the scene's signed auth chain today, so it gains a second form, body `{ "sessionTicket": string }`, validated with `AuthenticateSessionTicket` and recorded in `daily_guest_visit` with the PlayFabId as `address`. The Studio calls it once after every non-wallet login.

## Linking

All links are made while logged in, so the session ticket proves which account receives the identity. Nothing is ever merged: if an identity already belongs to another account with progress, the player is told and chooses which account to keep playing with.

### Add a wallet: `POST /api/link-wallet`

Body: `{ "sessionTicket": string, "address": "0x…", "message": string, "signature": string }` (message and signature from the nonce flow above).

Server: `AuthenticateSessionTicket` → current PlayFabId `C` (reject expired tickets); verify the signature like `login-wallet`; look the wallet up → `W` or none.

- No `W`: `Server/AddGenericID(C, {address})` + `UpdateUserData {address}` (what `initializePlayer` would have written). `200 { "linked": true }`. The client keeps its current login; from now on `login-wallet` and the scene's `get-login-id` both resolve to `C`.
- `W` exists and `C` has no progress: `200 { "linked": false, "CustomId": <W's CustomId> }`. The client logs in as `W`, stores that CustomId as its wallet login and forgets the guest id. `C` is left empty; `scripts/playfab-delete-orphan-accounts.js` removes it with the other orphans.
- `W` exists and `C` has progress: `409 { "error": "both-have-progress", "wallet": {level, tierSub, games}, "current": {level, tierSub, games} }`. The client shows both; **the wallet account always wins** (Decentraland progress is never abandoned by this flow). "Continue with the wallet" = the previous case, with the current progress left behind; "Not now" keeps playing unlinked. Moving the wallet onto the current account is not offered: it would strip the wallet from `W`, and the orphan script deletes wallet-less accounts.

`hasProgress(PlayFabId)` (server, `web/server/auth/`): `UserReadOnlyData.xp > 0`, or statistic `tier-sub > 0`, or `current_mission > 1`, or any `player_game` / `recorded_game` row for that PlayFabId.

### Add email or Google: client only

- Email: `AddUsernamePassword {Username, Email, Password}` on the current session (PlayFab requires a username there: the client generates `golfer_<8 hex>`, never shown).
- Google: `LinkOpenIdConnect {ConnectionId: "google", IdToken}`.
- A PlayFab "already linked to another account" error → the UI says so and offers to log in with that identity instead (and to come back to link a wallet to it). No automatic switch.

## Server rooms: trust the session ticket, not the client

Today `Season-Room` (`onCreate`, `onAuth`) and `season-party-lobby.resolveMember` find the account from `user.publicKey` through the `address` generic ID, and `Mission-Room.onAuth` / `gameLobbyRoom` take the `PlayFabId` the client sends, all unverified. Guests, email and Google players have no wallet, so the rooms switch to the ticket. The scene keeps it in `bootstrapped.clientInfo.sessionTicket` (`scene/src/meta/bootstrap.ts`), but today only the mission join passes it (`npc-storymode.ts`); the Season, party and `gameLobbyRoom` joins must add `clientInfo: { sessionTicket }` to their options (task 1.10). The Studio sends it in every join from the start.

- `onAuth`: `Server/AuthenticateSessionTicket {SessionTicket: clientInfo.sessionTicket}` → `UserInfo.PlayFabId`; expired or missing ticket → reject. The client-sent `PlayFabId` is ignored.
- `address` of the player, used for the game window gate, `player_game`, `recorded_game` (`POST /api/recorded-game`), tournaments and the ranking rows: `user.publicKey` **only if** `GetPlayFabIDsFromGenericIDs(address)` returns that same PlayFabId; otherwise the PlayFabId itself. So a guest's records are keyed by its PlayFabId, and the monthly allow-list (wallets only) never matches a guest.
- Rooms touched: `Season-Room`, `season-party-lobby` (its "Connect a wallet to play ranked" check goes away), `season-party-room`, `Mission-Room`, `GameLobbyRoom`. Until the scene deploy that sends the ticket everywhere is live, a join without `clientInfo.sessionTicket` falls back to today's lookup; then the fallback is removed.

## Client flow

1. Remembered login in `localStorage.golfcraft.auth` (`{ method, customId? }`, 30 days): wallet and guest re-login silently with their CustomId; email asks for the password again when the PlayFab ticket has expired; Google re-prompts through GIS.
2. Otherwise the login screen offers the four methods. Guest is one tap and lands in the menu; the menu then shows a persistent "Save your progress" prompt (wallet, email or Google) until the account has at least one of them.
3. Wallet: `GET nonce` → `personal_sign` → `POST login-wallet` → `CustomId` → `LoginWithCustomID`.
4. After any login: the same `InfoRequestParameters`, `initializePlayer` on new accounts, display name and `UserData.address` writes as `bootstrap.ts`.
5. Logout clears the stored login and the PlayFab session. For a guest with no linked identity, logout warns that the progress will be unreachable.

The stored `CustomId` is a credential equivalent to a session cookie: never log it, never put it in a URL. Guests lose their account when the browser storage is wiped or they change device, which is why step 2 keeps asking.

## What a player without a wallet does not get

NFT golf clubs, on-chain materials, Season prizes (wearables minted to a wallet by the bridge: they stay claimable until a wallet is linked) and the mission-6 emote. Coins, energy, xp, rank and PlayFab materials work the same.
